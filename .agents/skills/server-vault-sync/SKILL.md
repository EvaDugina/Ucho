# Синхронизация локального vault с сервером

Серверный `VAULT_HOST_PATH` — источник истины. Направление переноса данных:
**сервер → локальная машина**. Vault не является Git-репозиторием; его содержимое
не добавляют в Git. Раздел «Резервные копии» в корневом `README.md` описывает
формат снимков и команды `bot.backup`.

## Данные подключения

- Возьми из текущего диалога или запроси у оператора адрес сервера, имя
  пользователя, путь к папке с приватным SSH-ключом **и имя файла ключа** (либо
  полный путь к файлу), путь серверного vault или готового снимка, локальный
  каталог назначения и требуемую свежесть данных. Не угадывай файл ключа по
  содержимому папки. Если данные из контекста могут относиться к другому
  серверу, уточни их применимость.
- Эти значения существуют только во время выполнения задачи. Не записывай их
  в этот скилл или репозиторий и не выводи реквизиты подключения в отчёт.
  Ключ обозначай как `<KEY_PATH>`; не повторяй полный путь к нему.
- Используй ключ **только как аргумент SSH-клиента**. Не читай, не копируй,
  не хешируй, не конвертируй и не показывай ключ или содержимое его папки.
  Для `.ppk` используй PuTTY `plink`/`pscp`, для совместимого ключа — OpenSSH
  `ssh`/`scp` с пакетной аутентификацией только по ключу. Парольный вход и
  отключение проверки host key запрещены. При новом или изменившемся host key
  остановись и попроси оператора проверить fingerprint вне этого соединения.
- Не читай `.env`, токены и process environment. Попроси пути у оператора или
  используй уже подтверждённые пути из диалога; техническую схему смотри в
  публичной документации проекта.

## Правило fast-forward

До передачи данных сравни по относительному пути, типу объекта и SHA-256 три
состояния: последний **успешно синхронизированный** серверный `manifest.json`
(baseline), текущий локальный vault и новый проверенный серверный снимок.
Baseline храни как частные служебные данные вне vault и вне Git; обновляй его
только после успешного переключения локального хранилища. Не считай дату файла
или совпадение размера доказательством одинакового содержимого. Baseline от
другого серверного источника не используй как общего предка.

- Если локальный путь не менялся относительно baseline, прими состояние сервера:
  новый файл, изменение или удаление. Удалённый сервером файл сохраняется в
  прежней локальной копии для возврата.
- Если локальный и серверный путь имеют одинаковый тип и содержимое, конфликта
  нет, даже если оба изменились после baseline.
- **Новые данные не являются конфликтом:** путь, которого нет в baseline и на
  другой стороне, добавь с сервера либо сохрани локально без отправки на сервер.
  Локальные новые файлы не становятся от этого серверным эталоном; перечисли
  их в результате. Если новый путь появился с обеих сторон с разным содержимым,
  это конфликт.
- Любое иное локальное изменение существовавшего пути, которое отличается от
  серверного состояния, — конфликт. Сюда входят разные правки одного файла,
  локальное удаление против серверного файла, локальная правка против серверного
  удаления, столкновение файла с каталогом и имён, совпадающих на файловой
  системе назначения без учёта регистра.
- Если baseline ещё нет, для непустого локального vault разрешай только
  одинаковые общие пути и новые пути, существующие лишь на одной стороне.
  Разные общие пути считай конфликтами; не трактуй локально отсутствующий файл
  как доказанное серверное удаление. Пустой локальный vault можно заполнить
  проверенным серверным снимком.

**При хотя бы одном конфликте немедленно останови синхронизацию.** Не переноси
даже неконфликтную часть, не восстанавливай и не переключай локальный vault.
Опиши каждый конфликт относительным путём и причиной расхождения без вывода
содержимого файлов, затем жди решения оператора. Не разрешай конфликты выбором
«сервер всегда прав» и не обходи проверку повторным запуском.

## Порядок работы

1. Определи из запроса направление, серверный источник и локальный каталог для
   **всего** vault; уточняй только отсутствующие или противоречивые сведения.
   Проверь, что локальный каталог данных находится вне
   Git-репозитория или надёжно исключён из отслеживания. Покажи короткий план
   с источником, назначением, способом проверки и судьбой прежней локальной
   копии, не раскрывая реквизиты подключения.
2. Через read-only SSH проверь существование источника, размер, время снимка,
   свободное место и состояние локального назначения. Предпочитай готовый
   серверный снимок с `manifest.json`; проверь его командой
   `python -m bot.backup verify` **в Docker**. Недельный снимок может быть
   старше живого vault: сообщи точную дату, не называй его актуальным без
   проверки требуемой свежести.
3. Если нужна копия именно текущего состояния, согласуй паузу сервиса, если
   она ещё не разрешена оператором. Приостанови записи бота и создай новый
   снимок штатным `bot.backup` **в Docker** в отдельном временном каталоге,
   чтобы не запустить ротацию штатных резервных копий. Возобнови сервис сразу
   после создания снимка, также при ошибке, и проверь его состояние. Проверь
   снимок до передачи. Если паузу записей, место на диске или проверку
   обеспечить нельзя, остановись: копирование живого дерева может дать
   несогласованный результат.
4. **До передачи и любых изменений локального vault** останови локальные записи,
   собери хэши в Docker и выполни проверку fast-forward по правилам выше,
   используя серверный manifest без чтения пользовательских текстов. Держи
   записи остановленными до переключения, чтобы сравнение не устарело. Сначала
   составь полный список конфликтов. При непустом списке сообщи их суть,
   возобнови локальный сервис со старым vault и остановись; наличие новых
   бесконфликтных данных не разрешает частичную синхронизацию.
5. Только при отсутствии конфликтов передай снимок в **новый** локальный
   промежуточный каталог. Проверь его штатным `bot.backup verify` в Docker и
   восстанови в новый пустой каталог. Добавь туда локальные новые файлы,
   отсутствующие на сервере, без перезаписи общих путей; проверь итоговое
   дерево по ожидаемым хэшам. Не выводи пользовательские тексты в терминал.
6. Сохрани прежний локальный vault как отдельную доступную для возврата копию.
   Проверь абсолютные пути и переключи приложение на подготовленный каталог.
   На Windows переноси и переименовывай средствами
   PowerShell в одной оболочке; старую копию не удаляй. Штатный снимок исключает
   `.obsidian`: сохрани её как локальные новые данные без отправки на сервер,
   если нет конфликта путей.
7. Возобнови локальное приложение и проверь его работу и отсутствие vault-данных
   в Git. При неудаче верни прежний vault и не обновляй baseline. Лишь
   после успешной проверки сохрани новый серверный manifest как baseline вне
   репозитория. Сообщи дату снимка, результат проверки, состояние прежней копии,
   количество новых серверных и локальных файлов и расхождения без их
   содержимого. Не объявляй синхронизацию завершённой при незавершённом шаге.

## Стоп-условия

Не продолжай перенос при неопределённом источнике или назначении, ошибке SSH,
неподтверждённом host key, **любом конфликте**, повреждённом снимке,
недостатке места, невозможности сохранить прежние локальные данные или риске
копировать vault во время записи.
Не применяй `--delete`, принудительный reset и удаление старых копий как часть
этого процесса. Исполняемый код, проверку снимка и восстановление запускай
только в Docker согласно `AGENTS.md` проекта.
