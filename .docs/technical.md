# Technical — Ухо

## brunelleschi_stage

- Стадия: POC B
- Последнее обновление: 2026-09-20

## technology

- Python 3.12, aiogram 3.13, APScheduler 3.10, markdown-it-py 4.2.
- OpenAI-compatible LLM: OpenRouter при непустом `OPENROUTER_API_KEY`, иначе
  AITunnel. Primary/fallback задаются env.
- Файловый vault вместо БД; Git для данных не используется.
- Docker Compose — единственный runtime и тестовый контур.
- Контейнер работает с `TZ=Europe/Moscow`: локальные `datetime.now()` и имена
  версий `/about` получают московское время. `DAILY_TZ` отдельно задаёт зону
  расписания. Метка в имени raw-сессии остаётся в UTC, как описано ниже.
- Pydantic валидирует LLM JSON для personality.

Главные env: `TELEGRAM_BOT_TOKEN`, `OWNER_TELEGRAM_ID`,
`ALLOWED_TELEGRAM_IDS`, `VAULT_HOST_PATH`, `VAULT_PATH`, provider keys/models,
`DAILY_HOUR`, `DAILY_TZ`, reminder window, `DEBUG`, `BACKUP_HOST_PATH`,
`BACKUP_ENABLED`, `BACKUP_WEEKDAY`, `BACKUP_HOUR`, `BACKUP_KEEP`,
`BACKGROUND_JOBS_ENABLED`, `STARTUP_RECOVERY_ENABLED`, логирование и proxy.
Полный список с комментариями — в `.env.example`.

`DEBUG=true` по умолчанию выключает backup и фоновые startup jobs, но оставляет
ручной Telegram-диалог и файловую запись. Явные `*_ENABLED` переопределяют это.

## architecture

Монолитный async-бот с request-scoped user context.

Поток обычного текста:

1. Middleware проверяет whitelist и устанавливает `userctx`.
2. Handler разрешает explicit reply, затем pending книжной цитаты, затем активную
   сессию или свободную заметку.
3. `conversation_service` обязательно дописывает typed user event в
   `00_raw/sessions/<timestamp>_<uuid>.jsonl`, flush/fsync завершает запись до LLM.
   Из JSONL обновляется читаемая Markdown-страница для Obsidian.
4. `classify_mood` обновляет `01_mood/current.md` и месячный event-log до
   `process_answer` только при полном валидном ответе. Ошибка, неполный JSON или
   недостаток свидетельств сохраняют прежний mood; обработка ответа продолжается.
5. `process_answer` передаёт mood текущего сообщения нейтральному анализу,
   чтобы тот не принимал разовую эмоцию за устойчивую черту или регуляцию.
   Затем получает `personality_delta`, проверяет
   дословные цитаты по текущему сообщению и лишь затем создаёт `reaction` отдельным
   LLM-вызовом. Генерация видит результат анализа и mood текущей реплики, если
   классификатор смог его определить. Пустой анализ не заменяется догадкой.
6. `answer_service` принимает только дельты с дословной quote, выдаёт ID/raw event
   ID/status pending.
7. Реакция отправляется через `session_messages`, которое сохраняет assistant event.

Для `ask`, `reaction` и `about_present` системное сообщение собирается из
`prompts/base.md`, образа в `prompts/judas.md` и соответствующего режима.
`prompts/process.md` задаёт отдельный нейтральный анализ без роли; mood также
классифицируется нейтрально. `prompts/reaction.md` требует использовать результат
анализа для ответа по существу. Литературные события в `judas.md` описывают
характер; отношения с человеком напротив развиваются сейчас, без предрешённого
исхода. Никакое другое имя или титул не присваивается собеседнику.

`/ucho <текст>` создаёт новый `session_id` до raw-записи. Первая запись имеет
тип `note` и не получает `q_num` прежнего вопроса. Реакция становится опорой
для следующих сообщений этой сессии.

Имя файла получает UTC-время первого raw-события (naive timestamp остаётся как
записан) и UUID. Новые сессии используют свой UUID; для исторических строковых
`session_id` файловый UUID вычисляется стабильно через UUIDv5. Внутренние
`session_id` и `event_id` стабильны. Runtime принимает только текущую схему;
автоматических миграций старых имён файлов и `.psycho` больше нет.

`_session.json` содержит активный runtime и pending refs. `_state.json` содержит
номер вопроса, daily/reminder plan, upload wait, книжные toggles/scores/pending.
Полная переписка не дублируется в runtime-файлах.

`about_service` сначала повторно анализирует mood по последней содержательной
пользовательской записи (`answer`/`note`/`message`) и transcript её сессии до 24 000
символов. Команды не выбираются. Активный runtime не требуется; даты разных
часовых поясов сравниваются в `DAILY_TZ`. Без исходного текста mood не создаётся.
Этот анализ не добавляет ход в траекторию и не смешивает повторные `/about` между
собой. В журнале у каждого вызова отдельный `analysis_id`, `trigger: about`,
реальный `raw_event_id`, дата исходного текста `source_at` и дата анализа `ts`.
Снимок показывает обе даты (`source_at`/`analyzed_at`), чтобы историческая реплика
не выглядела оценкой состояния сегодня. Ошибка mood не блокирует профиль;
пользователь получает краткое уведомление, текущий mood и журнал сохраняются.

Затем при наличии pending-дельт выполняется нейтральный synthesis, после него —
представление пользователю. Сначала атомарно записываются
version/current, после чего захваченные pending-дельты получают status
`synthesized`. Handler сначала отправляет пересказ, затем сохранённый полный
профиль через `about_messages`: YAML-метаданные становятся блоком кода,
Markdown-заголовки — жирными, каждый HTML-фрагмент помещается в лимит Telegram.
Synthesis возвращает JSON с текстом и шестью обязательными характеристиками;
схема проверяет типы и диапазоны, неизвестные характеристики допускают `null`.
Полный предыдущий профиль, включая шапку, всегда является основой уточнения.
Обязательный массив `metadata_updates` перечисляет только изменяемые параметры:
`field`, точные `delta_ids` из переданных новых наблюдений и непустой `reason`.
Код отклоняет выдуманные ссылки и дубли полей. Значения остальных параметров
переносятся из предыдущего профиля дословно, даже если LLM вернула сокращённую
формулировку или null. Заполнение прежде неизвестного поля также требует основания.
Первый профиль формируется из дельт без предыдущей оценки; `metadata_updates` пуст.
Отсутствие подтверждения в новой партии не опровергает ранее накопленное знание.
При пустом наборе новых дельт `synthesize_about` возвращает прежний профиль без LLM.
Приложение собирает YAML-блок только из шести разрешённых русских полей;
`null` показывается как `...`, low/medium/high — как низкая/средняя/высокая.
Telegram timestamp перед сохранением имени версии переводится
в `DAILY_TZ`. Внешние Markdown-ограждения снимаются при чтении, записи и показе.
Ошибка синтеза оставляет текущий профиль и дельты без изменений.

При синтезе LLM получает два сообщения: system с правилами профиля и user
с полным текущим профилем и JSON-массивом всех pending-дельт. В дельтах передаются
аспект, вывод, дословная цитата, уверенность и служебные идентификаторы/время/статус.
Raw-история, вопросы бота, журнал настроения и книги отдельно в этот запрос не входят.
Промпт требует сохранять не опровергнутые сведения, оттенки и оговорки предыдущего
описания, уточнять конкретные выводы новыми фактами и не подменять стабильный тон
настроением последней реплики. Прежние оценки остаются рабочими гипотезами:
обоснованное опровержение возможно, сокращение только из-за отсутствия повторного
свидетельства в новой партии — нет.
Для пересказа второй вызов получает system из `base.md`, `judas.md` и `about.md`,
а user — полный сохранённый профиль. Без новых дельт выполняются mood и пересказ;
новая версия personality-профиля не создаётся.

### Значение полей анализа

Правила экстракции и границы категорий заданы в `prompts/process.md`:

| `aspect` | Содержание и ограничение |
|---|---|
| `character` | Устойчивая общая манера действовать; нужны повторяемость и отсутствие более точной категории. Не значение по умолчанию. |
| `speech` | Наблюдаемые лексика, стиль, метафоры, ирония и структура речи; без догадок о скрытых мотивах. |
| `emotional_regulation` | Способы обходиться с эмоциями, успокаиваться и восстанавливаться; не сама эмоция. |
| `relationships` | Близость, доверие, конфликты, взаимность и границы в отношениях. |
| `values` | Принципы, приоритеты и представления о допустимом. |
| `motivation` | Цели, интересы и прямо названные побуждения или препятствия действию. |
| `habits` | Повторяющиеся конкретные действия и распорядок. |
| `self_image` | Самоописание человека; не автоматически подтверждённая черта. |
| `triggers` | Связь конкретной ситуации с эмоциональной/поведенческой реакцией. |

Остальные поля дельты: `summary` — один осторожный вывод; `quote` — непрерывная
дословная цитата из связанного raw-ответа; `confidence` — оценка силы свидетельства
0–1, не вероятность истинности черты; `raw_event_id` — проверяемая ссылка на источник;
`id` — идентификатор наблюдения; `created_at` — время записи наблюдения;
`status` — pending до синтеза, synthesized после; `synthesized_in` и `synthesized_at`
— версия профиля и время включения. Все подтверждённые дельты остаются в
`02_personality/deltas.json`, включая уже синтезированные.

В начале профиля находятся шесть параметров в следующем порядке:

| Поле | Точное значение | Допустимые значения |
|---|---|---|
| **Регистр речи** (`register`) | Наблюдаемая лексика и способ выражения: разговорность, книжность, профессиональные слова, образность. | Содержательное описание или `null`. |
| **Тон речи** (`tone`) | Повторяющаяся окраска общения, не настроение последней реплики. | Содержательное описание или `null`. |
| **Открытость** (`openness`) | Самораскрытие именно в этой переписке, не психометрическая оценка. | 1 — минимум личного, 3 — избирательно, 5 — подробно о личном и уязвимом; 2 и 4 промежуточные, либо `null`. |
| **Переносимость провокаций** (`provocation_tolerance`) | Наблюдаемая реакция на реальные провокационные вопросы. | `low` — низкая, `medium` — средняя, `high` — высокая, либо `null`. |
| **Ход мысли** (`thought_flow`) | Как человек развивает высказанное рассуждение: связывает тезисы, аргументы и выводы, переходит между идеями, обобщает примеры, сопоставляет варианты, возвращается после отступления. | Краткое содержательное описание подтверждённого способа рассуждать или `null`; не оценка интеллекта, правильности выводов, скорости или скрытых процессов. |
| **Отношение к прямым вопросам** (`direct_questions_attitude`) | Предпочитаемый способ переходить к вопросу по существу, включая личные темы: сразу, после пояснения контекста или постепенно. | `welcomes` — принимает/просит прямые вопросы; `needs_context` — нужен предварительный контекст; `avoids` — предпочитает непрямой заход; `context_dependent` — явно зависит от темы. |

Отношение к прямым вопросам требует явной общей просьбы или нескольких согласующихся
реакций на вопросы собеседника. Разовая просьба сохраняет свой контекст; отсутствие
возражений, ценность честности и доверия не доказывают предпочтение. Прямота не
означает провокацию; `context_dependent` не заменяет неизвестное значение.
Ожидания от собеседника сохраняются в дельтах `relationships` с цитатой и контекстом.

Ход мысли опирается на наблюдаемые связи между идеями в дельтах `speech`;
самоописание отделяется от наблюдаемого рассуждения. Для устойчивой характеристики
нужны согласующиеся примеры; одиночный случай описывается с ограничением контекста.
Метафоры, длина реплики и эмоциональность сами по себе не доказывают способ рассуждать.
Неизвестное значение любого из шести полей отображается как `...`. При обновлении
сохранённой шапки удаляются два исключённых параметра, меняется обозначение
неизвестного и добавляется `Ход мысли: "..."`; тело и доказательные дельты сохраняются.

Mood: `sign` — приятность переживания (+/0/-); `energy` — активация (high/normal/low);
`direction` — направленность на себя/внешнее/без объекта (auto/hetero/neutral);
`quality` — наиболее подтверждённое переживание из 12 категорий; `dominance`
классификатора — ощущение контроля (high/normal/low), не агрессивность.
В журнале `valence`, `arousal`, `dominance` — численные оси от −1 до 1, а
`dominance_label` — словесная категория контроля. `n` — число оценок в агрегации,
не число всех сообщений. Обычный ход агрегирует до 40 оценок с затуханием 0.6
и весом прежнего снимка 2/(2+n). `/about` сохраняет одну оценку с контекстом.
`stability` — эвристика разброса знака: rigid при дисперсии <0.15, labile >0.75,
adequate иначе; при менее 3 оценках insufficient_data. Это не характеристика
личности и не медицинская оценка. Recovery не повторяет уже записанный анализ
того же raw-сообщения.

`books.py` без LLM разбирает EPUB/FB2/Markdown/TXT и строит версионированный
`structure.json`. EPUB использует nav/NCX, при их отсутствии — linear spine;
FB2 — верхние section основного body; Markdown — CommonMark headings; TXT —
абзацы в одном разделе с названием файла. Цитата
120–1200 символов никогда не пересекает верхнюю главу. Только после выбора
`BookExcerpt` диалоговый слой вызывает `ask_book_question`.

Оригинал, нормализованный текст, metadata и структура сохраняются под стабильным
`books/<book-id>`. EPUB ZIP не извлекается. Новая книга записывается во
временный каталог и становится видимой только после завершения всех файлов.

Ключевые модули:

- `handlers.py` — разрешённые команды, callback и precedence входящего текста.
- `session.py`/`session_log.py` — recovery state и единственный raw source.
- `moods.py`/`mood_file.py` — нормализация mood, current и месячные события.
- `about.py` — хранилище дельт и версий профиля.
- `books.py` — библиотека и персональное книжное состояние.
- `scheduler.py`/`daily_service.py`/`reminder_service.py` — фоновые сообщения.
- `recovery.py` — pending, queued и offline backlog.
- `backup.py` — снимки каталога, проверка хешей и ротация.
- `scripts/repair_books.py` — ручной осмотр и восстановление книжного индекса.

## instructions

### Локальный запуск

```powershell
Copy-Item .env.example .env
docker compose up -d --build bot
docker compose logs -f bot
```

### Развёртывание

`deploy/deploy.sh` подготавливает Docker-хост и отдельные каталоги данных и
копий, обновляет код, запускает проверки и поднимает compose. Подробности —
`deploy/README.md`.

### Тестирование

```powershell
docker compose build bot
docker compose run --rm -e VAULT_PATH=/tmp/ucho-test bot pytest
docker compose run --rm bot ruff check bot scripts tests
docker run --rm -v "${PWD}:/repo" zricethezav/gitleaks:latest detect --source=/repo
```

### Бэкапы

При старте создаётся снимок, если за текущую календарную неделю зоны `DAILY_TZ`
его ещё нет. Затем планировщик делает снимок раз в неделю: по умолчанию в
понедельник в 03:00 зоны `DAILY_TZ`. Если снимок за эту неделю уже есть,
планировщик пропускает запуск.
Операция синхронна внутри event loop, чтобы записи самого бота не пересекались
с копированием. `VAULT_HOST_PATH` и `BACKUP_HOST_PATH` — разные каталоги хоста.
Снимок сначала пишется во временный каталог, затем переименовывается;
`manifest.json` содержит размеры и SHA-256 файлов. Старые снимки удаляются
после `BACKUP_KEEP` готовых копий, максимум четырёх; лишние старые снимки
удаляются также при старте. Это локальная копия на том же хосте, без
автоматической отправки на другой сервер.

## quality

### Чеклисты

- Pytest покрывает команды/layout, raw-before-LLM/recovery, mood/personality,
  книги/reminders, `/leta` и backup.
- `tests/smoke/test_main_paths.py` проверяет чистый vault.
- Перед deploy обязательны полный pytest, smoke, Ruff и Gitleaks.

### Наблюдаемость и логирование

Python logging пишет stderr/docker logs и ротируемый `.logs/bot.log`.
`.ucho/log.md` хранит нейтральные операции без stacktrace для пользователя.

### Безопасность

- Whitelist применяется к message и callback.
- `/upload` и `/sea` дополнительно проверяют owner ID на командах, документах и
  callback из старых сообщений; меню и `/help` скрывают их от остальных.
- Секреты только в `.env`.
- XML DTD/entity запрещены; ZIP paths/объём/число членов проверяются.
- EPUB/FB2/Markdown/TXT разбираются локально; LLM не участвует в индексации,
  извлечении metadata или выборе фрагмента.
- Книжные ID и metadata проверяются до построения пути; symlink-книги отклоняются.
- Session ID ограничен безопасным набором символов до построения пути JSONL.
- Telegram/LLM dynamic output экранируется перед HTML.
- Производные profile/mood и книжный контекст передаются LLM как fenced user-data,
  а не как system prompt.
- Пользовательская запись без request-scoped uid отклоняется.
- `/leta` проверяет точный resolved path `users/<uid>`.
- Recovery, daily и reminder повторно проверяют действующий whitelist.
- Ручные/книжные/daily-вопросы, ответы, `/about`, reminder и `/leta` меняют
  пользовательскую сессию только под одним per-user lock.
- Durable merge-slot принимает текст только во время уже записанного raw-pending
  ответа; другие занятые LLM-операции возвращают busy без привязки к старой сессии.

## rules

## ai_pipeline

- `ask`: один вопрос голосом Иуды по теме или затравке.
- `ask_book_question`: вопрос только по уже выбранному фрагменту и его chapter
  metadata; полная книга модели не передаётся.
- `classify_mood`: categorical sign/energy/direction/quality/dominance.
- `process`: нейтральные personality deltas с цитатой из текущего сообщения.
- `reaction`: ответ голосом Иуды после mood и personality анализа.
- `synthesize_about`: нейтральный внутренний профиль.
- `about_present`: представление нейтрального профиля голосом Иуды.

Primary и fallback выбираются per task из env; специальных внешних скиллов нет.

## telegram_bot

Команды публикуются per-chat scope только доверенным. Владелец дополнительно видит
admin-команды. Polling не сбрасывает pending updates; startup сначала дожимает
pending/queued/offline сообщения, затем выполняет daily catch-up.
